# Run a spec-driven TDD cycle

The primary agent orchestrates. The approved spec is authoritative about intended outcomes. Black-box integration tests are the executable source of truth for externally observable behavioral acceptance criteria; unit tests support verification of internal rules and failure cases. Tests can be wrong: resolve disagreements against the approved spec rather than allowing unit tests or implementation details to redefine the external contract. Execute small coherent slices. Keep specs in repository files and progress/evidence in chat. This explicit-only workflow retains its separate cycle-level delegation approval even when ordinary delegation skills are active.

## Prepare and authorize

1. Locate the spec and actual user approval of its identified revision. Check its content against the approved revision/digest. File metadata alone does not establish approval. If approval or material decisions are missing, use `$write-spec` or ask for the missing decision; do not start dependent work.
2. Read `~/.codex/instructions/engineering.md`, `~/.codex/instructions/security.md`, `~/.codex/instructions/testing.md`, and `~/.codex/instructions/delegation.md`. Inspect repository instructions, relevant contracts, working-tree changes, test tooling, local and CI discovery patterns, and existing checks. Use codebase-memory for structural exploration when applicable. Preserve unrelated work; establish applicable security criteria and flag missing prerequisites.
3. Establish baseline results before edits. Record existing failures separately. They do not count as red for new criteria. Confirm exact commands discover the intended tests; a passing command that finds none is not evidence.
4. Map slices and criteria to verification and owners. Give each shared config, lockfile, fixture, schema, or generated asset one explicit owner. Do not delegate away integration execution. See [handoff and evidence formats](references/handoffs.md).
5. Propose bounded roles, files/responsibilities, completion conditions, and expected benefit in one cycle-level approval request. Include integration-test-writer and unit-test-writer where applicable, a distinct production-code-writer, mandatory preimplementation test-reviewer, and justified postimplementation specialists. Existing approval suffices only for the stated scope; invocation or spec approval is not delegation approval. Wait for an affirmative response before spawning. New roles or expanded scope need fresh approval.

If a role is unavailable or delegation is declined, report the limitation, stop dependent delegation, and continue permissible independent work under the shared standards. Self-authorship/review cannot satisfy this cycle's independent authorship/review gates; do not silently substitute the primary agent and claim a completed cycle. Newly added custom agents may require a new session to appear in the available role list; confirm availability rather than pretending a fallback role is the configured agent.

## Behavioral slice gates

Run these sequentially; a handoff is not proof of execution.

1. **Integration red:** assign black-box acceptance tests, fixtures, and controlled provider stubs to integration-test-writer. It must not start the app, integration suite, or infrastructure. Once assets are ready and statically checked, the primary agent confirms run readiness and executes the tests. Record the assertion, expected/observed result, criterion, command, and tested state demonstrating the required missing behavior.
2. **Independent acceptance-test review:** test-reviewer reviews integration coverage and red evidence against the approved criteria before production starts. Include any unit tests already available, but unit-test readiness or red evidence is not a prerequisite. Supply the explicit comparison base and stable reviewed state, including relevant staged and new/untracked tests, fixtures/configuration, and spec. There is no default review diff. Resolve actionable findings through the test owners, rerun affected red checks, and obtain focused re-review as needed.
3. **Implementation and supporting unit tests:** a distinct unit-test-writer authors isolated tests before or during implementation as domain/application interfaces become clear, independently deriving expectations from the approved spec and contracts. It may run scoped unit tests and safe static checks. Unit tests need not fail before production starts; neither their readiness nor a unit-red result gates implementation. A different agent instance, production-code-writer, owns only production behavior and explicitly assigned supporting files. Supply the spec, reviewed acceptance tests, agreed interfaces, and integration red evidence. It may run unit/static/build checks but cannot edit either test suite, spec, expectations, or snapshots. Neither test author implements business behavior. Coordinate interface decisions and serialize edits with runs/reviews of the affected assets.
4. **Integration green and completion checks:** after production and test authors report readiness, the primary agent executes integration tests against the built artifact and effective configuration. Require passing acceptance tests, applicable unit tests, and regression checks. Have test-reviewer review supporting unit tests added or changed after preimplementation review before completing the slice; unit coverage cannot replace integration acceptance coverage.
5. **Refactor and verify:** keep changes within approved scope and retain passing tests. Production refactors stay with the production owner; test refactors stay with test owners. Run affected regression checks and required risk-based review, then advance. Previously passing slices must remain green.

Only integration behavioral assertions establishing missing required behavior count toward the preimplementation red gate. Syntax, missing imports/symbols, compilation, discovery, readiness, and infrastructure failures do not establish red; resolve failures that prevent integration execution. A blocked supporting unit test is not a second preimplementation gate, but must be resolved before completion. The primary agent may create agreed signatures and inert scaffolding to make tests runnable, recording ownership and changes without implementing business behavior. Resolve new design decisions before scaffolding. Tests assert required outcomes, never an artificial `false` or a stub-specific error.

Supporting cases may already pass. If all criteria already pass, assess whether the requirement is already satisfied and record verification-only coverage; do not invent a red result, break working code, or claim a red-to-green implementation occurred.

## Technical and mixed slices

Follow the approved criterion-to-evidence mapping. Use a test author suited to the assets; do not invoke integration-test-writer solely to execute an existing suite. The primary agent executes integration and shared-infrastructure checks. For non-integration verification assets outside unit authorship, propose a bounded suitable author assignment with explicit ownership and approval.

- Demonstrate an unmet technical check before implementation where meaningful.
- For behavior-preserving changes, retain a passing regression baseline and establish the target technical outcome through the approved check, review, or reproducible experiment.
- Mark integration/unit stages not applicable only with criterion-specific reasons recorded before implementation. Missing credentials, infrastructure, or available agents are blockers, not applicability exemptions.
- Have test-reviewer assess the technical verification plan, assets, baseline evidence, and applicability decisions before production changes, including when no new tests are needed.
- Keep verification author and production implementer distinct. Do not manufacture failures or introduce unnecessary application test infrastructure. In mixed tasks, retain the integration red gate and supporting unit-test completion requirements for behavioral slices.

## Failures, review, and completion

Apply the shared integration execution and readiness requirements in `~/.codex/instructions/testing.md`. Before every integration run, confirm test-asset readiness, available relevant unit/static results, the actual source revision and built artifact, effective configuration, prerequisites, and resource availability. Supporting unit tests need not exist or pass for integration red; resolve issues that prevent the application or integration tests from running. At the red stage, anticipated feature assertion failures are expected; unrelated integration readiness failures still block. At completion, all applicable unit/static checks must pass. Freeze production, tests, and config during execution; serialize commands sharing mutable resources unless isolated. Use controlled test dependencies, safe diagnostics, and bounded waits.

Classify failures from evidence as production defects, test defects, contract discrepancies, or environment failures. Production authors report disputed assertions without editing them. Route test defects to their authors; never weaken criteria, skip tests, or update snapshots merely to obtain green. Obtain renewed spec approval for material contract changes, then revisit affected tests and gates. Stop dependent work on unresolved decisions or missing prerequisites while continuing safe independent work.

Select postimplementation specialists by affected concerns using the selection criteria in `~/.codex/instructions/delegation.md`, within the separately approved cycle assignments. Scope reviews to a stable revision plus included diff/untracked files (or an immutable snapshot); record checks against that state. Wait for reviews, resolve confirmed findings through owners, rerun affected checks, and obtain focused re-review. Do not mix evidence from changed states. Approval for the originally bounded review work need not be requested again.

Read the relevant sections of `~/.codex/instructions/reporting.md` before findings, handoffs, and completion reports. Maintain compact chat checkpoints using the reference format. On resume, revalidate spec approval, source/diff, assets/artifacts, available roles, and prior evidence; rerun invalidated checks, not every unchanged passing check. If approval/evidence cannot be recovered, ask rather than infer it.

Finish with criterion coverage, resulting behavior/technical outcomes, red/green or baseline evidence, passed/failed/unperformed checks, review status, and unresolved limitations. Completion requires all applicable checks and independent gates; distinguish verification-only work from red-to-green work. Invocation does not authorize commit, push, publication, deployment, production access, or destructive cleanup.
